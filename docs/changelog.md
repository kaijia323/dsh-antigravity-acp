## 0.3.2-fork.3 · 2026-11-19（kaijia323 fork）

- **新增：有界历史重放兜底（`replayFallback`，默认开启）**。旧行为是会话接不上一律报 `AGY_SESSION_UNRECOVERABLE` 永久失效；现在先照常尝试 `session/resume`，失败（历史被改写、取消/停止后游标失效、映射缺失等）才用 `boundedHistory()` 取**最近若干消息**（默认上限 120000 字符）新建 ACP 会话继续对话，并在日志里写明「按有界历史重放新建会话」。`replayFallback: false` 可恢复旧行为；`replayMaxChars` 调整预算。
- 真机复现（2026-11-19 19:18 会话 `fc799239`）：用户点「停止」中断一轮后，下一轮直接报「没有可用的会话映射」并永久失效。重放兜底后，同类场景会在下一轮自动重建会话继续。
- 真机 E2E（19:22，真实 agy ACP 账号，隔离 HOME）：改写历史触发 resume 失败 → 日志「原 ACP 会话无法接上，按有界历史重放新建会话」→ 该轮 `finish=stop` 正常完成；换 worker / 空闲回收 / 中途改档位三例同时回归通过。
- 说明：取消/停止仍会删除在途游标（本轮历史未落定），这是刻意保留的；区别是下一轮不再永久报错，而是重放恢复。

## 0.3.2-fork.2 · 2026-11-19（kaijia323 fork）

- **修复：换 worker / 映射被删导致的「没有可用的会话映射」永久判死**。连接池把同一对话换到另一个 worker、空闲回收、标题请求占用空闲槽都属正常行为，但 `SessionMapStore.claim()` 在 owner 变化时会**删除磁盘条目**，随后 `session/resume` 拿不到映射 → 报 `AGY_SESSION_UNRECOVERABLE`，且因为不重放历史，该对话永久失效。真机证据：2026-11-19 16:51（`09723820`，空闲 22 分钟）与 17:18/17:22（`eb012b6b`，空闲 32 分钟），`sessions.json` 里两条映射在失败瞬间被删。现在接管只换 owner、**保留条目**，旧 worker 下次处理该会话时只丢内存记录、不改磁盘。
- **修复：失败路径不再删除恢复映射**。`#resumeSession` 校验失败、MCP 桥被其他对话接管、异常终止、链接回收、prompt 构造失败都改为「丢内存 + 保留映射」，下一轮仍可 `session/resume`。仍会删除映射的只剩两处刻意场景：prompt 在途失效（`#advanceSession(settled=false)`，本轮历史尚未落定）与宿主删除 DSH 会话（`releaseConversation`，改为无条件 `purge`，重启后也能删）。会话迁移到其他 worker 时关闭本进程副本（配合已验证的「`session/close` 后可 resume」），避免两个进程同时持有同一 ACP 会话。
- **改进：模型/思考强度变化不再重建会话**。既有 ACP 会话直接 `session/set_config_option` 应用新模型与档位（复用路径新增这一调用）；`session/resume` 不再因路由指纹变化拒绝恢复，恢复后把指纹同步为当前值。system 提示与工具目录在会话创建时固定，沿用原会话——恢复映射优先于「指纹完全一致」。
- **新增单测**：接管不删条目、接管后旧 owner 写入/删除无效、磁盘条目在新 owner 写入前仍在。
- 验证：`npm run check` 通过（typecheck + 412 项单测 + 构建）。
- **真机 E2E（2026-11-19 18:04–18:08，DSH 0.2.2-rc.5 + 真实 agy ACP 1.5.0 账号）**：
  - 跨进程恢复（原有用例）：销毁 adapter 后用新实例 + 同一映射恢复并继续 ✅；
  - 换 worker（新用例，共享 `SessionMapStore`、进程 A 的 ACP 仍存活）：进程 B 接管后 `已恢复 ACP 会话` 并正常继续 ✅；
  - 空闲回收 600ms（新用例）：`关闭 ACP 会话（空闲回收，保留恢复映射）` → 下一轮 `已恢复 ACP 会话` ✅；
  - 中途思考强度 low→high（新用例）：`档位路由 … effort=high` 就地应用、`复用 ACP 会话` 继续 ✅；
  - DSH Web 真机（安装 fork.2 并重启宿主后）：Gemini 4 Neon 会话 2 轮正常，第 2 轮前把推理等级 Extra→High，会话继续并正确回答 ✅。

## 0.3.2-fork.1 · 2026-11-19（kaijia323 fork）

- **修复：DSH 用户插话（`busyEnter: steer`）会杀死会话**。DSH 在回合中途把用户插话作为真实 user 消息追加在工具结果之后；旧实现把它当成「历史被改写」，`#abandonTurn()` 丢会话后因中途没有磁盘映射直接报 `AGY_SESSION_UNRECOVERABLE`（真机 2026-11-19 15:11 复现：会话 `d7bdbc39` 第 18 步作废）。现在 `ContinuationState` 把「user 角色 + id 从未发出」的尾部消息（宿主通知与用户插话）排除在续轮判定之外，并把可投递内容附到最后一条工具结果交给 agent——插话不再丢失，也不会再判死会话。
- **修复：续轮期间的一次性通知被静默吞掉**。子代理完成 / 后台任务完成这类 `tool-jobs`、`subagent-settled` 通知此前在续轮里只被跳过、从未送达模型（`#advanceSession` 又把它们计入已发送），表现为「主代理读不到子代理结果」。现在按 form 跳过可重复的大块上下文（snapshot / catalog / instructions / recall），其余一次性通知与插话统一随工具结果投递（`tailDeliveryNote`）。
- **新增 `sessionTimeoutMs`（默认 120000）**：只作用于 `session/new` 与 `session/resume`。此前二者共用 `requestTimeoutMs=30000`，官方进程冷启动 / 多 worker 并发时子代理会报 `ACP 请求超时（30000ms）: session/new`（真机 2026-11-19 15:07 复现，子代理 `audit-backend`）；现在默认 120 秒，可用普通配置覆盖。
- 真机 E2E（2026-11-19 15:23–15:25，DSH 0.2.2-rc.5 + Gemini 4 Neon）：① 工具执行中插入 steer，回合正常 completed，助手回复 `6 × 7 = 42`；② 默认路由 Gemini 子代理成功启动并返回 `OK`，无 `session/new` 超时。
- 已知残余：会话取消 / worker 回收 / 上游挂起后的「无映射」路径仍按设计报 `AGY_SESSION_UNRECOVERABLE`（本 fork 暂未加入历史重放兜底）。

## 0.3.1 · 2026-11-19

- **删除选择器识别的名字猜测**：`findModelSelector` / `findThoughtLevelSelector` 此前在缺少 `category` 时回退到 `/model/i`、`/thought|effort|reason/i` 的名字匹配。真机确认（`agy acp` 1.5.10）：`session/new` 返回的三个 select（`model` / `thought_level` / `mode`）**全部带 `category`**，不需要猜。现在只认语义标签，缺标签返回 `undefined`，由调用方走「无可选模型 / 无独立档位通道」的显式失败。理由：名字匹配会把别的 select 误认成模型选择器，而错误路由不可逆。

- 新增测试：`model-selector.test.ts`（只认 category、名字误导时以 category 为准、分组展平）、`tier-suffix.test.ts`（新档位无需改代码即可折叠）。

## 0.3.0 · 2026-11-19

- **删除「判定注入块」的逻辑，改用 message id 确认历史身份**。0.2.2–0.2.4 三版都在修同一个枚举不完备的问题（0.2.2 只改比较侧；0.2.3 把 `source.form` 当有限枚举，漏了 `notice`；0.2.4 反转为「默认注入」但仍靠 `kind` 猜测）。根因在指纹只算 `role + content`、不算身份：两条消息文本一样就无法区分「中间插了一条」与「原来那条被改了」，只能靠来源类型去猜。现在指纹改为 `{id, role, content}`，宿主上下文按「`user` 角色 + id 从未发出去过」识别——不需要枚举来源类型，DSH 新增任何来源都自动生效。
- **去重同样改为按 id**：`incrementalMessages()` 不再按 `source.kind` / `source.form` 判断，内容相同但 id 不同的两条消息会被正确视为两条（此前内容去重会把用户重复发送的同一句话吞掉）。
- 依 **DSH 的稳定契约**：`id` 在消息创建时生成一次、写入会话日志、派生历史时原样返回（`dsh-session/src/surface.ts` 的 `case 'user/message': return event.data`），跨进程重启不变。已用真机实验验证：销毁 adapter 后用新实例 + 同一 `sessions.json` 恢复成功（`已恢复 ACP 会话 … 已发送消息=1`）。

## 0.2.4 · 2026-11-19

- **修复：注入块判定改为按来源，不再枚举 `source.form`**。0.2.3 用 `['snapshot','catalog','instructions','recall']` 白名单判断注入块，但 DSH 的 form 取值随版本与插件增长——实测本机历史里还有 `notice`（`tool-jobs` / `model-selection` / `plan-mode` / `ptc-mode` 等，共 143 条）。漏掉的类型会被当成「历史被改写」，整轮报 `AGY_SESSION_UNRECOVERABLE`。真机复现：2026-11-19 12:30 的会话，第 2 轮第 31 步来了一条 `tool-jobs`（后台任务完成通知）后立即失败。现在规则反转为「带 source 且 `kind` 不是 `user`（压缩检查点除外）即为注入」，新出现的来源类型自动落入豁免。
- **去重范围刻意保持不变**：`isInjectedContext()` 放宽只用于续轮与前缀校验；`incrementalMessages()` 的去重仍只针对快照/目录/指令/召回。`notice` 类每条都是一次真实事件通知，去重会让模型漏看「后台任务已完成」，省下的 token 换不来这个风险。带图片的消息同样永不去重（`ptc-mode` 可能是用户上传的图片引用）。

## 0.2.2 · 2026-11-18

- **修复：工具循环中途的宿主注入让整轮报 `AGY_SESSION_UNRECOVERABLE`**（真机复现于 2026-11-18 19:20 的会话）。DSH 的 pre-step 会把 `time-context`（默认 600s 墙钟到期）、`runtime-context`、技能目录与工作区指令追加到请求 `messages` 的**最后一条**；续轮判定原先只检查尾部是否连续 tool 结果，末尾一旦是注入块就返回空数组，续轮假失败 → `#abandonTurn()` 丢弃 ACP 会话与磁盘映射 → 下一轮因无映射失败，对话永久失效。现在 `isInjectedContext()` 统一认定注入块：`trailingToolResults()` 先跳过尾部注入块再找工具结果，`ContinuationState.accepts()` 剔除注入块后再比前缀；注入块本身仍正常发给 agent，真实用户消息与模型输出不获得豁免。

## 0.2.1 · 2026-11-18

- **删除全部历史重放路径**：会话接不上一律报 `AGY_SESSION_UNRECOVERABLE`（取消后也一样）——包括删除「用户取消后编辑提示词」的一次性重放例外与 `#cancelledKeys`。取消只保留 ACP 会话、下一轮按增量续上；接不上就请新开会话。原因：重放会把整段 DSH 历史（实测 287 个信封、单条工具结果 2MB）灌给上游，agy 按体积截断成 `<truncated N bytes>`，模型据此推断「会话中断/换了模型」，前几步都在重新对齐。ACP 的 `session/resume` 保持原样（不重放）。
- **删除 `reuseSessions` 配置**：不再有「每轮新会话 + 全量重放」的开关。旧配置里若仍写着该键会被忽略（不再产生重放）。
- **首次聊天不再写「历史重放」说明**：`<dsh-conversation-history>` 只在历史里真有 assistant / tool 轨迹时出现（压缩这类一次性请求），普通首轮只有用户消息与注入块，不再把当前请求误标成「重放」。
- **工具签名块补上 agent 侧的命名约定**：说明工具在 agent 声明里带 `mcp_dsh-tools_<会话后缀>_` 前缀，且声明里可能附加 `toolSummary` 这类 agent 元数据（不会转交 DSH）。此前签名块只写短名与参数，模型会误判「签名里的 bash/edit 没有声明给我」。
- **修复取消标记未清除**：`cancelled` 只豁免一轮输出指纹校验，回合完整交付后清除；此前取消过一次的会话会永久跳过 `outputMatches` 校验。

## 0.2.0 · 2026-11-18

- **进程与会话生命周期改用宿主原生能力**：删除插件自己的进程治理（owner 文件、`isProcessAlive` pid 探测、`cleanupStaleRuntimeDirectories`、`cleanupStalePyiTempDirs`）——启动/终止/退出确认全部交给 `ctx.subprocess` 的 `terminate()` / `waitForExit()`；运行目录只剩「给 PyInstaller 一个可写 TEMP」这一个职责。同时订阅宿主的 `session/disposed` 事件，在 DSH 删除会话时释放对应 ACP 会话与 `sessions.json` 映射，不再由插件猜清理时机。

- **并发模型改为「一对话一进程」，删除容量与队列**：真机探针证明官方 agent 单进程能并发多个会话（5 路并发，含每路 3–4k 输出的长回答），但插件仍按对话分配独立链接——每条链接各自持有 MCP 桥、工具授权代次与 prompt 生命周期，合并成一个进程会让一次卡死带走所有对话。因此删除 `maxConcurrentSessions` / `queueTimeoutMs` 与整个等待队列：不再有「第 3 个对话排队 120 秒后失败」，进程数改为跟随活跃对话数。
- **空闲回收恢复为默认 15 分钟**：早先关闭它是因为回收后要重放整段历史；现在 `session/resume` 已在真机验证（含 `session/close` 之后仍可恢复），回收后不再重放，代价只是一次 resume。会话数量因此不设上限：196 个会话都能接着聊，常驻进程只剩活跃对话。

- **实测：同一账号 5 路并行不触发 429**。用独立 ACP 客户端对真 `agy acp` 1.5.10 跑了两种形态：
  单进程内 5 个会话并发 → 5/5 `end_turn`（5.9–8.9 秒）；5 个进程各 1 会话并发 → 5/5
  `end_turn`（9.1–12.0 秒）。两次都没有 429。结合 11:24–11:28 两路并发零 429 的结果，
  “并行会话数”不是 2026-11-18 00:59 那次 `RESOURCE_EXHAUSTED` 的充分条件；该次成因仍未查明，
  不能拿“降低并发”当结论。实验脚本是临时探针（`/tmp`），未入库。
- **再加一轮长回答并发**：同一进程内 5 个会话同时生成 1200–1800 字长文（实测每路输出 3.0k–3.9k
  tokens、总 11.7k–12.7k），5/5 `end_turn`，耗时 63–72 秒，647 条 `session/update`，仍然零 429。

- **额度失败不再展示上一次的旧值**：服务端不再把上一次成功快照标成 `stale` 继续
  返回，失败就是 `status: "error"`；浏览器端也删掉了同样的合并逻辑。额度要么是
  本次取到的，要么明确报错，不展示可能已经过期的数字。
- **文档同步已删配置**：`autoDownload`、`keepProcessAfterCancel`、`session/load`
  退路这些已经不存在的字段与路径从 `configuration.md` / `reference.md` 移除；
  `resumeSessions` 默认值改为 `true` 并说明它是唯一延续路径。

- **空闲回收默认关闭**（`idleRecycleMs` 默认 `300000` → `0`）：池的上限就是 `maxConcurrentSessions`，常驻内存本来有界（单 worker 实测 250–370 MB，容量 2 合计约 600–800 MB），而回收换来的那点内存要付出三层代价——下一轮冷启动、整段历史全量重放（实测一次 1007 条），以及最坏的情况：模型被重放的历史带回旧任务，把用户的新消息当背景。2026-11-18 12:01 的实例：turn 3 结束 11:55:18，空闲 5 分钟在 12:00:18 回收；用户 12:01 发来订阅链接，会话重建后重放 1007 条，模型在 turn 4 的第一步继续去读自己上一轮的中间产物，CoT 全程没提那条链接。需要内存优先的场景仍可显式设成 300000 之类的值。取消不再回收进程（见下一条）。

- **中断不再销毁会话（真机验证）**：用独立 ACP 客户端对官方 `agy acp` 1.5.10 实测——
  `session/cancel` 后 prompt 返回 `stopReason: "cancelled"`；`session/list` 仍列出该会话；
  `session/resume` 成功；取消确认后**在同一会话立刻再发 prompt 也能正常 `end_turn`**（实测 8.2s）。
  但**不等 `cancelled` 应答就发**会被 agent 明确拒绝：`the running prompt is being cancelled;
  wait for it to finish, then send this prompt again`。所以取消宽限必须等确认，不能提前发；
  取消后编辑提示词仍然只能重建（ACP 没有历史回滚），这是编辑的语义而非回退。

## 0.1.53 · 2026-11-18

- **账户串行与失败语义**：并发取凭据时共享换发不再绑定先到者的 `AbortSignal`（一个请求被取消不再把其他等待者判成未登录）；换发失败会在状态里留下可读原因，不再出现「界面已登录、请求说未登录」而没有任何解释。
- **工具结果不再被改写**：历史里出现没有匹配调用的工具结果时明确报错（`INVALID_ARGS`），不再把它当普通用户文本发给上游。
- **错误原因与日志**：上游错误事件（429 / SAFETY / 上下文超限）不再被半截工具调用参数的 `PROTOCOL_DRIFT` 顶掉；代理模式构包失败的异常分类不再一律报成图片准入问题；代理行日志回调补上脱敏。
- **资源回收与缓存自愈**：prompt 构造阶段失败时当场关闭刚建立的 ACP 会话并归还磁盘 claim；同版本二进制缓存损坏时可自愈（清掉损坏目录后重试一次）；流式下载中断上报真实原因（不再用 `arrayBuffer()` 二次失败掩盖）；凭据原子写的临时名改用 UUID + `'wx'`。
- **ACP 单帧上限**：stdout 的行缓冲此前没有上限，对端吐出一条永不换行的超长行（畸形输出或二进制垃圾）会让内存一路增长；现在按 **64 MiB** 判定协议违规并关闭链路（口径对齐社区 magpie / agy bridge 实现），失败原因保留 `AGY_PROTOCOL_VIOLATION` 而不是笼统的「链接关闭」。
- **工具 schema 的两处上游拒绝形态**：① DSH 的工具参数会带同一 schema 内部的本地引用，原实现把 `$ref` 当未知键丢掉，参数结构退化成空对象；现在按 JSON Pointer（`#/properties/…`）、`$defs` / `definitions` 名字展开，引用节点的 `description` 覆盖被引用节点，解析不到时退化为无字段 object，循环引用由深度上限截断。② 对象节点带**兄弟 union**（`{type:object, properties:{…}, oneOf:[{required:[…]}]}`，只表达字段互斥）时，原实现按类型联合会折叠掉整个对象、丢掉 `properties`，上游随即要求 `input_schema.type: object` 而 400；现在保留对象结构并丢弃该 union。两处口径都来自 magpie 直连实现对同一形态的处理（其 issue #4046/#4561）。
- **上游指纹诊断（只读）**：magpie 生态的实测结论是 Antigravity 会把「请求文本里出现已知客户端指纹」（`x-anthropic-billing-header` 计费行、Claude Code / Agent SDK 身份句、`system-directive`、`RFC 2119` 等）的请求统一伪装成 `429 Resource has been exhausted`，换账号与等额度都无效；而 magpie 本体对 Code Assist 反而**保留**计费行（去掉它是为了别的厂商的前缀缓存命中率），两派做法互斥。本包不选边：代理模式只扫描本轮 system 并在命中时记一条诊断（仅规则 id 与次数），**不改写**任何请求内容；命中指纹时若上游回 429，错误文案会直接说明「可能是被拒绝的提示词指纹而不是额度耗尽」（magpie 对同一现象的态度也是如实告知，而不是让用户追着额度跑）。
- **身份指纹打散（可选，默认关闭）**：新增即时开关 `cloakSensitiveWords`。照 magpie 的实测口径（其 `googleTurnsAway` 词表与 `antigravityCloak` 算法，输出逐字符对齐）：命中区间内的 ASCII 词段在首两个字符后各插一个零宽空格，只作用于 system 指令、不改用户消息，去掉零宽即还原原文。属于绕过上游识别，默认关闭。
- **账号被停用不再当作「未授权」**：403 且上游写明 `violation of Terms of Service` / `disabled in this account` 时不再换发登录态重试，直接报 `AGY_ACCOUNT_SUSPENDED` 并说明需要申诉。
- **三路静态审查后的修复**：① 指纹打散改用只降 ASCII 的小写（`toLowerCase` 对 `İ` 这类字符会变长，用降级串的下标切原串会错位，最坏情况是「日志说已打散、文本原样上行」）；② 打散与诊断覆盖整条 system 指令（`options.system` 与 `role: system/developer` 的消息——Codex 的身份句正是以后者进来的），且诊断读的是实际发出的文本、不再与打散状态自相矛盾；③ 429 只有在读到的上游原话确实是 `Resource has been exhausted` 时才做指纹归因，其余如实报限流并带上脱敏后的上游原话；④ 账号停用识别覆盖流内 error 事件与刷新后的第二次 403（payload 保留有界的上游 message）；⑤ 同版本二进制缓存自愈只在 `EEXIST`/`ENOTEMPTY` 时清目录重试，其余错误带原因抛出；⑥ 代理账户副本的原子写与凭据/缓存/会话映射统一用 UUID 临时名，共享换发的 `finally` 先挂 `catch`（不留无 handler 的 rejection），设置卡片的代理专属开关在 ACP 模式隐藏。

## 0.1.31 · 2026-10-30

一轮可靠性加固，均为既有行为的缺陷修正，不改变对外配置字段与协议契约。

- **额度取数不再可能永久卡住**：HTTP 回退的换发与 Cloud Code Assist 请求此前没有超时。并发刷新会合并到同一个在途 promise 上，一次挂起的请求就让额度药丸永远停在「读取中」，手动刷新也救不回来。现在各有 20 秒上限，超时折叠成可读的失败快照并释放在途状态。
- **401/403 重试改按状态码判断**：此前靠匹配错误文案里的 `HTTP 401` 字符串，文案一改就静默丢掉「换发后再试一次」。`QuotaError` 现在携带 `status`，判断只看状态码；非 401/403 的失败不再触发无谓换发。
- **非法代理不再让插件装载失败**：此前 apply 一开始就同步解析 `proxyUrl`，保存了非法地址后重启宿主，插件加载即失败——而修正它的设置卡片正是本插件贡献的，用户只能手改配置文件。现在装载期只告警并继续加载，真正用到代理时各自失败（启动 ACP 报 `AGY_INVALID_PROXY`）。
- **运行期代理地址变坏按 Promise 拒绝**：插件自身的 `fetch` 与 CLI 取数入口此前会在同步阶段抛错，调用方的 `.catch()` 收不到。现按各自契约返回 rejected promise，由既有的「折叠成可读错误」路径处理。
- **恢复会话失败时归还磁盘 claim**：认领会话映射后若启动失败，所有权会残留到卸载。新增 `SessionMapStore.unclaim`，恢复与建轮两条失败路径都归还，别的 worker 可立即接管仍有效的条目。
- **单条畸形 JSON-RPC 帧不再判死整条链路**：无法路由的消息此前抛 `PROTOCOL_VIOLATION`，被消息泵当成流读取失败，链路关闭、对外报 `LINK_CLOSED`，所有在途请求一起失败。现在只丢弃该帧并留痕，链路与在途请求不受影响。带 id 却缺 `result`/`error` 的畸形响应单独处理：命中在途请求时立即按 `AGY_PROTOCOL_VIOLATION` 拒绝它，而不是丢弃后让那个请求白等到超时。
- **中止错误码统一**：连接池的 `AGY_TURN_ABORTED` 改为与适配器、协议层一致的 `AGY_ABORTED`。两者同属 `AGY_` 前缀，原本就不会命中宿主的重试词表，此处只消除排障时的语义分叉。
- **zip 解压加压缩炸弹上限**：条目数、单条目与解压总量三道守卫，并在写盘前判定。中央目录谎报解压大小的包由 yauzl 的大小校验拦下（构造用例已覆盖）；另按实际流出字节数加了兜底，用于该校验被关闭或换实现时的纵深防御。官方包远低于上限。
- **细节修正**：OAuth client 元数据多份并存时按出现顺序配对（此前固定取第一个 secret，可能与所选 client id 不配套），同一 secret 重复出现时也不会配错；MCP 桥 Bearer 头改常数时间比较；`parseTokenState` 去掉重复查询；额度超时文案在不足 1 秒时报毫秒，不再显示「超过 0 秒」。
- **验证边界**：本地类型检查、38 个文件 / 658 项隔离测试与构建通过。真实 Desktop GUI、官方账号与非 Windows 实机未重新验收；未用真实官方 zip 或真实对端造过异常输入，畸形帧与解压上限均由构造用例覆盖。

## 0.1.24 · 2026-10-22

### 日常使用

- **有界并发池**：默认最多 2 个按需启动的独立 worker，可设 1–4；同会话工具结果回原 worker。等待队列最多 64 项，默认 120 秒，支持取消；主对话优先于排队中的后台标题。
- **先登录再取模型**：「连接 / 登录 ACP」建立不发送 prompt 的发现会话，验证连接并读取目录。无 CLI 时也可从已有 ACP 登录态刷新；目录、上下文容量与图片能力跨 worker 同步。
- **原生图片输入**：通过宿主附件服务发送当前 / 历史消息与工具结果中的图片，协商上游能力，校验引用、媒体类型与字节数。支持 PNG、JPEG、WebP、GIF；已卸载图片明确说明没有像素。

- **更可靠的设置草稿**：远端更新保留 dirty 字段，仅提交修改项，显示冲突，遵守只读状态并防重复保存。
